# Decision Log

Part of the [TUI implementation guide](./README.md). Append-only. Consult when a
rule looks arbitrary or you are about to reverse one; the reason is recorded here.

| Date | Decision | Reason |
| --- | --- | --- |
| 2026-09-16 | Store resources as JSONC, and preserve comments across every rewrite | A format that accepts comments but discards them on the next write is worse than one that rejects them: the reader types a note, it parses, and it is gone by the time they look again — because reading a resource stamps `LastAccessed` and rewrites the file. So tolerance alone was not on offer. `System.Text.Json` has no comment-preserving document model and putting trivia on the models would push an on-disk concern into every type, so the comments are lifted off the previous file, anchored to the member they sit against, and spliced back into the serialised output. A comment whose member the rewrite removed goes with it, which is right: it was written about something that no longer exists. Blank lines are not preserved; they anchor to nothing, and guessing would be worse than a stable shape. |
| 2026-09-16 | Keep `state.json` plain JSON while the resources became JSONC | Nobody writes it. It is the registry, the current workspace and pane layouts, rewritten whenever any of them move, and the file already has a sibling — `settings.toml` — for everything a person types. Giving it comment support would advertise an invitation the file does not mean. |
| 2026-09-16 | Hand the `:json` editors the file's own text, not a re-serialisation of the model | The editors existed to show the reader the raw resource, and re-serialising quietly stripped exactly what JSONC was added to keep, before the reader ever saw it. They now open the bytes on disk. The way back needed the same care: a comment typed during the session is in the editor's output and nowhere else, so the flow stages that text through `IStraumrFileService.CarryCommentsFrom` and the service's own write picks the comments off it. Writing the edited text to the resource first and letting the save normalise it was the alternative, and it would have left a half-applied edit on disk whenever the save was refused. |
| 2026-09-16 | Pin a foreground on the inverted selection surface, rather than letting it invert whatever is already in the cell | Inverting with no foreground of its own reads best in principle — it is exactly the terminal's two colours — but it is not implementable safely. A `Style` cannot reset a foreground to the terminal's own: `Color.Default` is indistinguishable from "unset" and overwrites nothing, so a cell that already carries a colour keeps it. A dialog's surface fill sets a background and leaves foregrounds alone, so a focused button inside one inverted whatever text of the screen behind happened to lie under it — Browse came out green because a "last used" line was beneath it, Create grey, and Cancel correct because nothing was. Pinning the foreground makes the band that colour deterministically wherever it is drawn. On a dark scheme the pinned white and the terminal's own foreground are the same thing to look at, which is why the fault only showed as stray colour rather than as a different design. |
| 2026-09-16 | Let `:theme <name>` set the theme, writing the one key through the TOML syntax tree | Reopening a file in an editor to change one word is the wrong amount of ceremony for the setting people will change most, and the developer asked for the command. It is the single exception to the program never writing the settings file, and it is made safe by not serialising: `SyntaxParser` round-trips a document byte for byte, so replacing one value leaves every comment, blank line and table where the reader put them — proved against the shipped template, which keeps all 27 of its comment lines and comes back byte-identical when set back. It is also more precise than editing the text would be: the template mentions `"terminal"` inside a comment, and a replace would have changed that too. |
| 2026-09-16 | Keep `text-bright` and `muted-bright` real colours even where the selection inverts | Setting both to `default` made the inverted selection band a single clean tone, and quietly took the colour off everything else those roles reach — every button label, the dropdown, the text a field is typed into, the badge. A button rendered as bare `[bold]` with no foreground at all, which is what the developer saw as an odd grey character. The roles are not only "text on the band", so they cannot be tuned as if they were. The band is now very slightly two-toned instead, which on a dark scheme is the difference between white and the terminal's own foreground. |
| 2026-09-16 | Write no migration code while the product is in early access | A legacy reader, a notice naming the settings that moved and a delete-the-old-file step were all written and then removed on the developer's call: the standard is not set, there is no installed base to carry, and the cost of the machinery is paid forever by everyone reading the loader afterwards. Renaming a file by hand once is cheaper than a compatibility path that outlives the reason for it. Revisit when there is a release anyone has upgraded from. |
| 2026-09-16 | Rename `options.json` to `state.json`, and the types with it | "Options" and "settings" are the same word, so a reader with both files in `~/.straumr` had no way to guess which held the workspace registry — and neither did anyone reading the code. The file now says what it is: state the program writes, versus settings a person writes. Nothing reads the old name: this is early access and the standard is not set, so a rename is a rename and an existing `options.json` is simply stale. `StraumrOptions` became `StraumrState` and the service and its `Options` property followed, because a type named after the wrong file is the same confusion one layer down. |
| 2026-09-16 | Move the default workspace and secret paths out of state and into settings | They were user configuration living in a file the program rewrites on every pane drag — there is even a `straumr config workspace-path` command for setting one, which is as clear a statement that something is configuration as exists. They are `[paths]` in `settings.toml` now, which makes the split true rather than merely stated: what is left in `state.json` is the registry, the current workspace and pane layouts, none of which anyone would type. |
| 2026-09-16 | Make `config workspace-path` report rather than set, and refuse a path with an explanation | The value it used to write is in a hand-written file carrying comments, and serialising a model back over it would strip every one of them — which is the whole reason state and settings are separate files. A command that silently ignored the path would be worse than one that says where the value lives, so passing one is refused, with the line to add and a non-zero exit. |
| 2026-09-16 | Report at startup what went wrong before there was a footer to report it on | A settings file that would not parse, or a theme that would not resolve, used to start the app in the default colours and say nothing: the host applied the theme before the shell existed and dropped the message on the floor. The shell now takes an announcement it makes on its first pass. This was found while writing migration code that was then thrown away; the gap it exposed was real either way. |
| 2026-09-16 | Make every role optional over the terminal theme, and add no `extends` key | A theme should be the differences, not a copy: changing one colour should not mean owning eighteen and never seeing an improvement to the built-in again. The terminal theme is the right thing to layer over because every one of its roles defers to the reader's scheme, so an unwritten role can never land somewhere the file did not account for — and it is the only palette of which that is true. An `extends` key was considered and dropped on the developer's call: the one case it buys, starting from deepocean, is served by `:theme export deepocean` and editing the copy, and that is also what stops export from being a command with nothing to do. A theme that fixes its own background while leaving `text` inherited is the one trap this opens, and it is warned about rather than forbidden. |
| 2026-09-16 | Split `accent` into accent, `brand` and a `[methods]` table | One role was doing three unrelated jobs — the key colour in the footer, the `{straumr}` wordmark, and POST's method colour — which went unnoticed while all three wanted the same blue. Making the accent colourless for the chrome silently took the identity mark and one method colour with it, and the screen went white. Colour that decorates and colour that carries meaning are different decisions and now have different roles. Methods get a table of their own rather than borrowing the semantic hues, because the method is the first thing a reader looks for in a list of requests and it should not be reachable only through whatever `accent` happens to be. Both are optional, as every role now is. |
| 2026-09-16 | Keep the chrome colourless but let the meaning-bearing colours use the terminal's palette slots | Drawing a method colour from the reader's own sixteen is not the imposition that a chosen accent is: the slots *are* their scheme, already tuned to it, so nothing reads as foreign. The rule is therefore about what a colour is for rather than about how much colour there is. Structure — keys, markers, rules, bands — stays colourless in the terminal theme; anything that tells the reader something is allowed a slot. |
| 2026-09-16 | Set the framework `Theme` on the running app's root, and use `Theme.Terminal` for a palette that defers to the terminal | Painting every Straumr style correctly is not enough: the framework clears every cell it owns with the theme's background, and `Theme.Default`'s is a dark blue. The first terminal theme therefore rendered as a solid navy rectangle over a transparent terminal — correct colours drawn on a ground nobody asked for. `Theme.Terminal` has a null background and foreground, and null means the renderer emits no colour at all, which is the only thing that leaves a transparent terminal transparent. It is set on `app.Root` rather than on the shell's own tree because dialogs and popups live in sibling layers. The setter is `SetStyle(Theme.Key, theme)`; an earlier reading of this codebase recorded that no setter existed, which was wrong — it is the generic keyed overload rather than a property. |
| 2026-09-16 | Give the terminal theme colourless chrome, and invert the selected row rather than colour it | A scheme the app cannot see may be built around any hue, so every hue the theme introduces of its own is a guess at somebody's taste; a cyan accent on a red scheme reads as a foreign object, which is what the first attempt did. Keys, markers, rules and badges are therefore the terminal's own foreground, dimmed or brightened, and the hues that remain are the ones that carry meaning — the method colours, a populated count, the active workspace, an error. |
| 2026-09-16 | Mark the focused selection by inverting the terminal's colours, through a `selection = "invert"` value that is not a colour | The developer asked whether the band could be inherited from the terminal rather than chosen. It cannot be read: no terminal reports its scheme to a program portably, `TerminalInstance.BackgroundColor` is the writer's own SGR state rather than a query, and the framework exposes no OSC round trip. But it can be *swapped*. `TextStyle.Invert` on the band gives the reader's own two colours with guaranteed contrast and no hue at all, which is what the terminal already does for its own selection and what vim and less do for a current line. Verified to compose: the attribute survives under the row's text and fills the focus chip's padding. The one selection that has nothing to invert against, text selected inside a field, keeps a colour of its own by falling back to the raised surface. The inverted surface pins a foreground; see the row below for why it must. |
| 2026-09-16 | Let the terminal theme drop the unfocused selection band as well as hover | The same argument that removes hover removes this one: there is no tint of an unknown ground among sixteen colours, and `text` being the terminal's own foreground means no concrete band can be guaranteed to read against it — a band that works on a dark scheme inverts on a light one. The selected row of an unfocused list is marked by its bar alone, which is a cue that costs no assumption. |
| 2026-09-16 | Make the terminal's own colours the default theme, and keep the blue palette as `deepocean` | The app is about to be handed to people who have already chosen a terminal scheme. Painting over it with one fixed dark blue is the sort of thing a tool earns resentment for, and a light-terminal reader got a dark rectangle in their window. The sixteen palette slots and `Color.Default` are the only values that follow a scheme the app cannot see, so the default theme is written entirely in those. The previous palette is not gone, only named: `deepocean` is the same eighteen hex values, proved identical by dumping every style before and after. |
| 2026-09-16 | Make `StraumrStyles` a facade over a style set rather than convert its call sites | Roughly 250 references across 36 files read `StraumrStyles.MutedText` and friends. Rewriting them to `StraumrStyles.Current.MutedText` would have been a mechanical change to almost every screen file for no gain at the point of use, and would have buried the real change — where the colours come from — in the noise. The static members became forwarding properties over a `StraumrStyleSet` instance, so the diff is two files plus the theming folder, and the before/after comparison of all 59 members is a meaningful test rather than a formality. |
| 2026-09-16 | Rebuild the shell on a theme change instead of repainting it | Framework styles are immutable values handed to a control when it is constructed, not bindings it re-reads: `commandBar.SetStyle(...)` and every `with`-built style captures its colours once. There is no way to repaint a retained tree, so rebuilding is the only option. (The framework's own `Theme` *can* be swapped — `SetStyle(Theme.Key, ...)` — but that governs only the cells no Straumr style reaches, not the controls.) The shell and its screens became scoped registrations so one scope holds the whole tree and the next one replaces it; everything they depend on stays singleton, so the registry, options and the applied theme survive. The reader is put back on the screen they were on. |
| 2026-09-16 | Put settings in a hand-written `settings.toml`, separate from `options.json` | They are different kinds of file with different authors. Options are the app's own state — the workspace registry, the current workspace, where pane dividers were dragged to — rewritten whenever any of that moves. Settings are the reader's, and people keep these in dotfile repos. Merging them would mean the program rewriting a commented file every time a divider moved, which no format survives. TOML rather than JSONC because it is the format that is pleasant to hand-edit: comments, sections, no quoted keys and no comma discipline. |
| 2026-09-16 | Take Tomlyn rather than hand-roll a TOML subset | The binary publishes ahead of time and single-file, so the bar was trim safety, and a hand-rolled parser would have met it. It would also have been wrong within a week: people who keep dotfiles write real TOML — multi-line strings, arrays, inline tables — and a subset parser answers those with a confusing error. Tomlyn 2.10.1 has a source-generated `TomlSerializerContext` that mirrors the existing `StraumrJsonContext` pattern exactly, compiles with zero trim/AOT warnings under `IsAotCompatible`, and is by the same author as the terminal framework. Its binder matches the property's own name, so every key is named explicitly with `[TomlPropertyName]`; without that, `Colors` looks for `[Colors]` and silently finds nothing. |
| 2026-09-16 | Define the built-in themes as TOML text rather than as constructed palettes | One definition of each theme instead of two, exporting one is writing the text out, and the files a reader starts from have been through the parser their edits will go through. It also makes the built-ins a standing test of the format. A malformed built-in throws rather than starting half-painted, since that can only be a mistake made in this repository. |
| 2026-09-16 | Let the terminal theme drop the hover band rather than guess at a tint of the background | The three row levels need a band fainter than the background, and the sixteen colours contain no tint of a background the app cannot see. Every candidate breaks somewhere: `black` inverts the hierarchy on a light terminal, and `bright-black` is the one portable dim and is already spent on muted text, which would then be invisible on the band. Dropping the faintest level — pointer hover — keeps the two that carry selection and keeps them correct on light and dark alike. A theme that names its own background, as `deepocean` does, still has all three. |
| 2026-09-16 | Warn about colliding roles instead of rejecting the theme | A theme that paints accent in the selection colour is not invalid, it has just made the marker on the selected row invisible — and that is close to undiagnosable from the running app, where the reader sees nothing rather than something wrong. The pairs the shell paints one on top of the other are checked and named on the footer, and the theme still applies, because refusing someone's colour choice is not this program's business. |
| 2026-09-16 | Open the real settings file in `$EDITOR`, not a temporary copy | Every other external edit in this app hands over a temp file, because what is being edited is a resource the reader addresses by name rather than by path. Settings are the opposite: the reader knows where the file is, may already have it open, and their editor's history and per-path configuration should apply to it. Nothing is written back afterwards — the editor saved it, and writing over that would be the edit being discarded. |
| 2026-09-16 | Carry non-RGB colours as themselves all the way to the cell | `Color.ToHexString()` answers a palette colour with a hardcoded xterm approximation and `Color.Default` with black, so the one place a colour is written into text — `KeyMarkup`, for a command-bar hint — had to stop using it or the default theme's key hints would be painted in a colour the reader's scheme never chose. The markup parser accepts a bare index and reads it back as the same palette slot, so the token is written by colour kind. `Brush.Solid` rejects `Color.Default` outright; the field is nullable and the framework's own default for it is null, so a theme that defers to the terminal simply does not paint through a brush. |
| 2026-09-16 | Let the shell own which screen claims stray focus, and put stray focus back on the visible screen every pass | `AutoFocus` bound over `FocusScope.IsReachable` answered the right question only while the list was in the tree. Every reload detaches it — the list lives in the `ComputedVisual` that swaps in the loading message — and a binding evaluated on a detached visual walks no ancestors: it answers true and registers no dependency that could invalidate it again, so a hidden screen's list stayed a permanent claim on every stray focus. Which screen is on show needs no binding to track; the shell already assigns `Root.IsVisible` and now assigns `FocusTarget.AutoFocus` with it. The invariant is held centrally rather than by each screen re-focusing itself after each delete, save and refresh, because focus is lost twice in those flows — when the dialog closes and again when the reload detaches the list — and `AutoFocus` alone cannot re-home focus that is stranded on a detached visual rather than null. |
| 2026-09-16 | Skip absent workspace files when scanning known secret references, as Workspaces already does | The developer's four-workspace warning came entirely from stale registry entries for removed files. Counting those as unreadable contradicted the collection shown by Workspaces. Existing corrupt files and failures reading a present workspace's resources still indicate incomplete coverage. No registry entries are removed by the scan. |
| 2026-09-16 | Keep Secrets independent of the active workspace, and index references across all registered workspaces on load | The store is global. Requiring an active workspace would hide valid secrets, while scanning only that workspace would understate the effect of a rename or deletion. The scan uses Core's non-stamping reads, records field locations rather than values, excludes cached auth results, and reports unreadable workspaces/resources. Selection only reads the index. Startup primes hidden-screen completion even when the active workspace is absent. |
| 2026-09-16 | Use the existing resource editor for secrets, with a fixed mask in inspection and the shared credential field in the form | Name and Value need no new editor infrastructure. The overview never shows the value or its length; the form follows Auths' mask/reveal-on-focus behavior. Copy creates a new identity and asks for a new name. Renaming does not rewrite references. JSON edits are validated before saving, so an invalid edit or changed ID leaves the stored secret untouched; a missing registered file can be restored under its existing ID. |
| 2026-09-16 | Give every screen action a typed command in its own namespace, named after the CLI's verb | The namespaces already made one screen's commands reachable from another; only four of them existed, so `:ws use` worked from Requests while `:rq edit` did not, and which actions crossed a screen boundary was an accident of what had been needed so far rather than a rule. Every action now has both forms — the key for the reader standing on the screen, the name for the reader who is not — and the vocabulary is the CLI's `create`, `copy`, `delete`, `edit`, `import`, `export`, so one program is not two languages. Each takes its subject by name and falls back to the selection, which is what the key does. `new` and `activate` are aliases, not second names |
| 2026-09-16 | Let the screen report that it opened a full-screen surface, rather than the command declaring that it will | The return stack has to be balanced: one push for one close. A command flag claimed the push before the command ran, and the moment `edit` could go two ways — the form for a request that reads, the external editor for one that does not — the flag was a guess. A create refused for want of a workspace opens nothing either. `TransientScreenOpened` is raised beside the `Show` that opened it, so the push and the close that pops it come from the same event. It also decides what a command from another screen leaves behind: Workspaces raises neither event because its dialogs are not screens, so `:ws delete` leaves the reader on Workspaces looking at what it did |
| 2026-09-16 | Take focus for a dialog in its own `Show`, rather than leaving it to `AutoFocus` | `AutoFocus` is applied on the render after `Show` and only where nothing else holds focus. That was enough while every dialog was opened by a keystroke, but a dialog opened by a typed command is shown in the middle of the pass that then restores focus after navigating, which would land the keyboard behind a modal with no way back to it. The full-screen views already focused themselves for the same reason. The shell also stopped asking the focus chain alone whether a modal is up, since the chain cannot answer until focus has reached one |
| 2026-09-15 | Edit resources through a structured form, keeping `$EDITOR` as the route to the JSON itself | The stated non-goal was an in-terminal *JSON* editor, and that still stands: nobody should have to hand-balance braces to add a header. A form over typed fields is the opposite of that — it is what makes a resource editable without knowing the file format, which is the reason the TUI exists beside the CLI. The external editor keeps the cases a form cannot reach: a field the form does not offer, a bulk edit easier as text, and a file too broken to load into fields at all. `e` picks between them by whether the request parses, because that is the same question. |
| 2026-09-15 | Build one editor kit rather than an editor per resource | The CLI's request, auth and secret flows are the same program three times: a working copy, a menu of `Label: value` rows, a per-field editor, and a save through Core. Every field they use falls into seven kinds, and auth — eleven OAuth2 fields, a nested request inside Custom — is what proves that set complete rather than merely convenient. Writing requests concretely first would have meant discovering the same set twice. |
| 2026-09-15 | Never put a character gesture on an ancestor of a focusable text field | Commands are collected up the focus chain, and a command runs before the focused control sees the key, so any bare letter between a text field and the window root fires while that field is being typed into. `PagedPane` put `t` on the node above every page, and typing a name containing one changed page mid-word. This is the second time the codebase has hit it — `BrowserDialog`'s dialog-level `n`/`r`/`d` fired while its path editor had focus, and were moved down onto the list, a sibling of the editor rather than an ancestor. Where there is a sibling, move the gesture to it; where there is not, as on a pane whose pages are all forms, the gesture stops being a character and carries `Ctrl` as a control byte. The check is mechanical: list every `AddCommand` between a text field and the root. |
| 2026-09-15 | `Tab` moves between fields in an editor, not between its pages | On a read-only paged view the titles are the only thing on the rule that can be stepped to, so `Tab` keeps its one meaning. A form breaks that premise: its fields are focusable, and `Tab` is the key every terminal form moves between them with. `PagedPane` therefore takes the choice as a parameter, and an editor leaves changing page to `t` and to the clickable titles. Giving pages the `Tab` would have left the fields reachable only by pointer, which is the one input a terminal cannot be relied on to have. |
| 2026-09-15 | Save on `Ctrl+S`, with no letter beside it | Every printable key belongs to whichever field has focus, which is why `s`, `c` and `y` stop at the form's edge. `Escape` closes and `Ctrl+S` saves, both delivered as the control character a terminal actually sends, with the letter-and-modifier form registered beside it unpresented. `Ctrl+S` is also XOFF on a tty with flow control enabled; that is the one risk in it, and the reason it is flagged for a terminal check rather than assumed. |
| 2026-09-15 | Report a successful save on the screen behind the editor, and a refusal on the editor itself | They are different events. A save that worked is done with the form — the view closes, the saved request is selected on the list, and that footer is where the reader is looking. A refusal is about a field on the form and has to be corrected there, so the view stays open holding the work and says why on its own footer. Closing on a refusal would discard exactly the text that needs fixing, which is the mistake the external-editor path already had to be corrected for. |
| 2026-09-15 | Store a multipart file part as `@path` and choose it with the existing file browser | Core already reads that encoding and the CLI already writes it, so the form is not inventing a format — it is giving the format a picker. `BrowserDialog` was built generic for exactly this, and typing an absolute path by hand into a single-line field is the part of the CLI flow most worth removing. The path is checked when it is chosen, while whoever chose it is still looking at it, rather than at send time when the picker is long gone. |
| 2026-09-15 | Require an exact screen name or explicit alias for navigation | Unique prefixes are useful for local actions, but `w` changing the entire screen is too broad and conflicts conceptually with the Workspaces selection alias. A per-command prefix policy keeps ordinary command convenience while making the navigation vocabulary exactly `workspace` / `ws` and `request` / `rq`. |
| 2026-09-14 | Model full-screen command results as transient children with a stack-based return target | A response opened by `request send` belongs to the screen that issued it, but naming Workspaces in Request code would make the next screen repeat the same exception. Marking the command as opening a child and letting its owner report close gives the shell enough information to push and restore the actual source; a stack also preserves the right semantics if transient views become nested. |
| 2026-09-14 | Treat identifiers as one quoted command argument and forbid double quotes in request names at the Core boundary | Whitespace cannot delimit both an identifier and later arguments without quoting. Completion owns presentation, so it wraps whitespace-bearing candidates and the shared parser hands handlers the original name. A literal double quote would require a second escaping language across TUI, CLI and persisted names; rejecting it in Core create/save keeps every request name representable, including copies and editor saves. |
| 2026-09-14 | Make singular `workspace` / `request` the canonical screen commands and noun namespaces, with `ws` / `rq` as aliases; allow workspace `use` to run in place from Requests | The CLI nouns are singular, so the prompt should display the same vocabulary rather than `workspaces` / `requests`. The former noun-based item selection commands move to `select` (`w` / `r`), removing ambiguity. A bare noun shows its screen and most nested commands navigate before dispatch; `workspace use` is different because its useful result in Requests is the new workspace's request list. It therefore activates through the existing Workspaces handler, reloads Requests, and never changes visibility. Prompt completion is synchronous, so a workspace-context change reloads all hidden screens before the next input; this primes both workspace and request namespace candidates without coupling the mechanism to either screen. |
| 2026-09-14 | Cycle a full-screen view's pages with `Tab`, and leave its movement keys unadvertised | `Tab` means "move the chip along the rule" everywhere in this app. On a screen whose rule carries pages rather than regions there is nothing else to step to, so giving `Tab` that job keeps one meaning for the key instead of inventing a letter beside it; a command claims the key before focus traversal reaches it. The hint it needs was made room for the way the resize keys already did it: the four movement hints are silent there, the keys still work, and the row reads as the screen's actions. |
| 2026-09-14 | Build a full-screen view from the shell's pieces and put its page titles on the rule that closes its bar | A modal that fills the terminal is a screen, so it reads as one: no frame title of its own, the identity header naming it, a three-row bar, a pane, and the one-row footer. A titled rule stacked over a tab strip named the region twice and lit two cues at once — the section's focus chip and the selected tab's accent — while costing the body a row. On the rule there is one title per page, the selected one carries the chip, and the rule is the tab strip it is everywhere else. |
| 2026-09-14 | Keep sends in a viewport-sized modal response view and allow cached expansion with `v` | The developer requested space for body, headers, animated sending and network statistics; staying open preserves failures/results, and viewing a cached result must not resend a potentially mutating request. Reuse the shared preview with wrapping; only the inline preview remains bounded. Body formatting and clipboard actions are scoped to the body focus target. Header and body durations come from Core measurements rather than simulated network phases. |
| 2026-09-10 | Implement one screen at a time, beginning with Workspaces | Keeps the rewrite reviewable and establishes reusable shell patterns first |
| 2026-09-10 | Use Core services directly from TUI application logic | Prevents CLI presentation concerns from leaking into the TUI |
| 2026-09-10 | Prefer framework controls, bindings, templates, and commands | Preserves retained-mode behavior and avoids duplicating framework machinery |
| 2026-09-10 | Keep external-editor workflows outside Core | Core owns model load/save; terminal integrations own editor orchestration |
| 2026-09-10 | Preserve `IncludeTui=false` | Keeps a compact CLI-only publish available |
| 2026-09-10 | Keep headers minimal and show the active workspace at right | Matches the approved layouts without invented status information |
| 2026-09-10 | Show only recent requests in the Workspaces detail preview | Keeps the pane relevant to workspace usage |
| 2026-09-10 | Do not use `ListBox<T>` for multiline resource cards | Version 3.9.0 measures and arranges every list item at a fixed height of one row |
| 2026-09-10 | Use the approved mockup colors as a shared application palette | Default control colors and button treatment do not preserve the mockup's hierarchy or contrast |
| 2026-09-10 | Build the shell from one window frame plus rules and surface tints | Nested bordered groups with gaps read as separate widgets instead of one screen |
| 2026-09-10 | Paint column dividers and surface tints with `Canvas` | Version 3.9.0 has no vertical rule control and no per-visual background |
| 2026-09-10 | Compose screen bars from `Grid` instead of `Header` | `Header` forces bold slots and its own surface color |
| 2026-09-10 | Trim list paths with a leading ellipsis and names with a trailing one | The tail of a workspace path identifies it; the head of a name does |
